# drizzle/

Database migrations, generated by `drizzle-kit` from `src/server/db/schema.ts`. **Don't write or edit these by hand.**

| Path | What it is |
|---|---|
| `0000_init.sql` | The first migration: every table, enum, index and check constraint in the schema. |
| `0001_verification_tokens.sql` | Adds `verification_tokens` for admin magic-link sign-in. |
| `0002_single_name.sql` | Replaces `people.first_name`/`last_name` with one `name` (filled as `first_name || ' ' || last_name`), makes `organizations.country` nullable and keys the unique index on `lower(name)`, `coalesce(country, '')`. Generated, then given the backfill `UPDATE` by hand before it was applied anywhere. |
| `meta/_journal.json` | The ordered list of migrations. `drizzle-kit migrate` uses it to know what's been applied. |
| `meta/0000_snapshot.json` | The schema as of each migration. `db:generate` diffs against the latest snapshot to write the next migration. |

## Commands

```bash
npm run db:generate              # after changing schema.ts: writes drizzle/NNNN_<name>.sql and a snapshot
npm run db:generate -- --name add_lead_source   # same, with a readable name
npm run db:migrate               # applies pending migrations to DATABASE_URL (reads .env.local)
```

`db:generate` doesn't connect to a database. `db:migrate` needs `DATABASE_URL`, and stops with a clear error
without it. It's for local and Neon-branch databases.

## Production

Production is migrated on every production deploy: Vercel's `npm run vercel-build` runs
[`scripts/migrate-on-deploy.mjs`](../scripts/migrate-on-deploy.mjs) after a successful `next build`. It applies
pending migrations with drizzle's migrator, over `DATABASE_URL_UNPOOLED` (or `DATABASE_URL` if that's unset), in one
transaction. If one fails, the deploy fails naming the file, nothing from that deploy is applied, and the previous
deployment stays live. Preview deploys skip it, since they share production's database. So a merged migration
reaches production with the code that needs it; don't apply it there by hand.

## Rules

- A schema change and its generated migration go in the same commit and PR.
- **Never edit or delete a migration once it has been applied anywhere** (a teammate's database, a preview, or
  production). Fix forward with a new migration.
- Neon branches are cheap: test a migration on a fresh branch before merging (merging to `main` deploys it to
  production).
- The snapshot files are large and machine-written. Joseph's reviewer leaves `drizzle/meta/*` out of its PR size
  count.
